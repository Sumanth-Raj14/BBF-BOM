## Genuinely missing, ranked by weight to a BOM/PLM buyer comparing against OpenBOM

1. **Effectivity (date / serial / lot)** — the only CRITICAL that is still substantively absent. One
   `effective_date` on the ECO header is not effectivity; there is no `effective_from`/`effective_to` on
   `bom_items_master` and no serial- or lot-break model. Any regulated or serialized-product buyer
   disqualifies on this. Note OpenBOM itself scores ❌ here — but Arena, Teamcenter and Windchill do not.
2. **Automated change notifications** — the table and the read endpoint exist and are wired to the client,
   but nothing on the server ever writes a notification row, so approvers are never told an ECO is waiting.
   This makes the whole approval workflow pull-only. It is also the cheapest fix on this list: one insert in
   `perform_eco_action` plus a `NotificationQueue` row to reuse the existing email dispatcher.
3. **Multi-UOM with conversion** — genuinely nothing at any layer. Blocks correct roll-up whenever a BOM
   mixes each/metre/kg/sheet, which is normal for mechanical and sheet-metal BOMs. The `exchange_rates`
   pattern is a ready-made template.
4. **MBOM as a usable object** — three tables and a model with no routes and no UI, so "EBOM vs MBOM" is not
   demonstrable even though the schema anticipates it. This is the row most likely to be tested live in a
   bake-off against OpenBOM's xBOM story.
5. **Part lifecycle state machine** — `part_lifecycles` and `lifecycle_definitions` are orphan tables; the
   product ships a flat `parts.status` string with no transitions, no history, no enforcement.

### Cheap wins already paid for (backend done, UI missing)

Deviations/waivers (8 routes + full API wrapper, no screen), BOM variants (3 routes + wrapper, no screen),
`POST /parts/check-duplicates` (server detector unused while the UI runs its own weaker heuristic), and
`GET /eco/{id}/impact` (wrapper exists, nothing renders it). Wiring these four costs UI work only and moves
four rows off the gap list.

- `frontend/src/components/advanced/ECRScreen.jsx:57` displays approval state derived from ECO status rather
  than from the `eco_approvals` rows the backend actually maintains.
